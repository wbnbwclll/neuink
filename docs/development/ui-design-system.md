# NeuInk UI 设计与交互规范

> 状态：项目级权威规范（v1）  
> 适用范围：`apps/desktop` 中所有新增界面、界面重构和交互修改  
> 说明：本文定义后续实现标准，不代表当前所有历史界面已经符合标准。旧界面在被修改时应逐步收敛，不要求脱离具体任务一次性重写。

## 1. 产品体验目标

NeuInk 是面向长期阅读、研究和知识整理的 Windows 桌面工作台。界面应当像可靠的生产力软件，而不是营销页、AI 演示面板或卡片展示站。

所有界面遵循以下原则，按优先级排序：

1. **信息和任务优先**：用户首先看到当前对象、状态和下一步操作。
2. **行为可预测**：点击、拖动、保存、关闭和切换在不同模块中使用同一套语义。
3. **高信息密度**：通过层级、对齐和留白建立秩序，不用大卡片和大图标制造稀疏感。
4. **状态可信**：加载中、未保存、保存中、已保存、失败和只读必须准确且互斥。
5. **渐进呈现**：常用操作直接可见，低频操作进入菜单；详情可以悬停预览，但不能只靠悬停访问。
6. **复用优先**：优先使用仓库已有组件、库、工具和交互模型。
7. **桌面优先**：以键鼠、分屏、可调整区域、长列表和长时间连续使用为主要场景。

## 2. 实现来源与复用顺序

实现 UI 前，按以下顺序检查，不得跳过已有能力直接创建新组件或引入新依赖：

1. `apps/desktop/src/components/ui/` 中的共享组件；
2. 已有业务共享组件和 hooks；
3. 已安装库提供的能力；
4. 在共享层扩展已有组件；
5. 仅当以上均不适用时创建新的业务组件；
6. 仅当现有依赖无法可靠完成任务时引入新依赖。

当前前端基础设施：

| 需求 | 首选能力 | 使用要求 |
| --- | --- | --- |
| 基础控件 | `components/ui` 中的 shadcn 风格封装 | 业务组件不要重复实现 Button、Dialog、Menu、Input、Table 等基础控件 |
| 无障碍交互原语 | `radix-ui` | 如果已有本地封装，必须使用本地封装，不直接使用 primitive |
| 样式与布局 | Tailwind CSS、`cn`、现有 CSS 变量 | 不在业务组件中建立第二套颜色、圆角或阴影系统 |
| 变体管理 | `class-variance-authority` | 多处使用的尺寸或状态必须收敛为变体 |
| 图标 | `lucide-react` | 不混用其他线性图标库，不用图标代替无法理解的概念 |
| 富文本与 Markdown | Tiptap 及现有 extensions | 先扩展现有编辑器能力，避免并行引入另一套编辑器 |
| 长列表 | `@tanstack/react-virtual` | 先测量性能；达到实际瓶颈后复用现有虚拟化能力 |
| Toast | 现有 `useToast` / Sonner 基础设施 | 同一动作不得同时弹多个重复通知 |

新增依赖必须在改动说明中回答：

- 当前仓库为什么无法完成；
- 新依赖替代了什么，而不是重复了什么；
- 体积、维护、许可证和 Tauri WebView2 兼容性；
- 是否提供了行为测试和回退策略。

## 3. 视觉基础

### 3.1 颜色与表面层级

颜色来源以 `apps/desktop/src/styles/theme.css` 为准。组件应使用语义类，不直接复制当前十六进制值。

| 层级 | 语义 | 推荐实现 |
| --- | --- | --- |
| 应用背景 | 工作区之外的底色 | `bg-background` |
| 主内容面板 | 用户实际阅读、编辑和浏览的区域 | `bg-card` 或 `bg-white` |
| 次级区域 | 工具条、筛选条、表头、分组背景 | `bg-muted` |
| 悬停 | 可交互行的轻量反馈 | `hover:bg-muted` 或 `hover:bg-accent` |
| 选中 | 当前对象或活动视图 | `bg-accent`，配合文字或边框，不只依赖颜色 |
| 浮层 | 菜单、Popover、HoverCard、Dialog | `bg-popover` |

强制规则：

- 主内容区域应与应用背景有清晰层级；默认使用白色内容面板和浅灰应用背景。
- 固定表头、粘性工具条和滚动覆盖层必须使用**不透明背景**。
- 不在承载正文、列表或表格的区域使用玻璃拟态、背景模糊或半透明渐变。
- `primary` 只表示品牌、主要动作、焦点和选中状态，不用于大面积装饰。
- 成功、警告、错误和信息状态使用 `success`、`warning`、`destructive`、`info` 语义变量，不随主题色改变含义。
- 除数据可视化外，不新增随意颜色；数据颜色必须有图例或直接标签。

### 3.2 字体与字号

使用 `theme.css` 定义的 Geist / Segoe UI / Microsoft YaHei UI 字体栈。

| 内容 | 建议字号 | 约束 |
| --- | --- | --- |
| 页面或对象主标题 | 16px | 单行优先，过长截断并提供完整信息 |
| 区域标题 | 13–14px | 使用字重建立层级，不重复加背景卡片 |
| 正文和表格内容 | 13px | 默认密度基线 |
| 次要信息 | 11–12px | 保证对比度，不低于 10px |
| 状态栏极简信息 | 10–11px | 只用于非关键、短文本 |

不要通过同时增大字号、加粗、加色和加背景来表达同一层级。通常选择其中一到两项即可。

### 3.3 间距、尺寸与圆角

- 优先使用 4、8、12、16、24px 的间距节奏。
- 紧凑列表行高为 32–40px；多行信息行高通常不超过 48–56px。
- 默认按钮使用现有 `Button` 尺寸：`xs`、`sm`、`default`；不要在业务组件重复写相近尺寸。
- 页面内容内边距通常为 12–16px；同级区域保持一致。
- 使用现有 `--radius` 和组件圆角。只有 Badge、状态点和明确的胶囊筛选项使用完全圆角。
- 普通内容区域优先用边框分层；阴影只用于菜单、Dialog、拖动预览和真正悬浮的面板。

## 4. 页面与布局

### 4.1 信息架构

页面从上到下最多包含：

1. 一个页面/对象标题区；
2. 一个主操作或筛选工具条；
3. 一个承担主要任务的内容区；
4. 必要时存在的状态栏或详情面板。

同一页面不要重复出现多个含义相近的标题、模式切换和操作栏。主任务开始前的固定区域原则上不超过两行。

### 4.2 表格和资源管理器式列表

- 高密度对象集合优先使用明细列表或表格，不为每个对象创建独立大卡片。
- 层级结构采用“当前目录的直接子项”语义；默认文件夹优先，再显示文件或条目。
- 标题列左对齐，数字、状态和操作列按统一规则对齐。
- 长标题截断，但必须通过原生 `title`、Tooltip、HoverCard 或详情面板提供完整值。
- 表头固定时必须不透明，并有明确底边线。
- 横向滚动只能属于内容表格区域；一个区域只允许一个横向滚动容器。
- 滚动条应在该内容区域底部可达，不得制造页面级和表格级双滚动条。
- 最后一行仍需保留底部边界，空白区域不伪装成额外记录。

### 4.3 卡片

Card 用于以下场景：

- 聚合一组独立指标；
- 显示可单独理解的摘要；
- 表达有明确边界的设置组或空状态。

Card 不用于：

- 可以用紧凑行表达的文件、笔记、标签或文献列表；
- 给每个小控件额外套一层视觉容器；
- 仅为了“看起来丰富”而增加图标、阴影和大留白。

## 5. 组件使用规范

### 5.1 按钮与图标

- 一个区域只有一个主要动作使用默认主按钮。
- 次要动作使用 `outline` 或 `ghost`；破坏性动作使用 `destructive`。
- 纯图标按钮必须同时提供准确的 `title` 和 `aria-label`。
- 图标只用于帮助识别动作或对象类型。无法改善识别速度的装饰图标应删除。
- 同一动作在不同页面使用同一个 Lucide 图标。
- 不用颜色和图标替代清晰动词，例如优先“保存”“移到回收站”，不只显示图形。

### 5.2 工具栏

- 常用、与当前选择直接相关的动作保留在工具栏。
- 低频文件操作、显示设置和高级格式进入 DropdownMenu 或 Popover。
- 工具栏尽量保持单行；空间不足时允许横向收敛或进入“更多”，不要无限换行压缩正文。
- 工具按钮应在不可用、只读、保存中状态下统一禁用，不能只禁用正文输入。
- 相同功能不应在同一视图的多个工具栏重复出现。

### 5.3 菜单、悬停详情与提示

- Tooltip 用于解释图标按钮或被截断的短标签。
- HoverCard 用于补充对象详情，但核心操作和关键信息必须可点击访问。
- ContextMenu 用于对象级动作；在正文编辑区域不得覆盖系统复制、粘贴和拼写菜单。
- DropdownMenu 用于低频命令，Popover 用于需要短暂填写或选择的内容。
- 浮层必须使用 Portal、正确层级变量和完整键盘交互，不自行硬编码极大 `z-index`。

### 5.4 Dialog 与危险操作

- Dialog 只用于需要用户做出决定或完成集中输入的任务。
- 删除优先使用回收站；不可恢复或会覆盖内容的动作必须说明后果。
- 按钮顺序保持一致：取消、破坏性/替代动作、主要确认动作。
- 不用 Dialog 展示普通成功消息；成功使用内联状态或短 Toast。

### 5.5 表单和状态

- Label 描述字段含义，placeholder 只提供示例，不能替代 Label。
- 错误显示在对应字段附近；页面级错误才放在页面状态区。
- 加载、空状态、失败、只读和无权限使用不同文案和视觉。
- 同一个异步动作只能有一个可信状态来源，避免按钮、Badge 和 Toast 相互矛盾。

## 6. 交互规范

### 6.1 点击、选择与打开

- 单击选择或打开必须在同类对象中保持一致。
- 行内按钮不得同时触发行点击；事件边界必须明确。
- 双击只用于用户已有桌面心智模型的场景，并同时提供单击可发现入口。
- 当前选中、键盘焦点和悬停是三种不同状态，不得共用同一视觉表达。
- 关键动作必须支持键盘访问，并显示 `focus-visible`。

### 6.2 拖动与调整大小

所有拖动实现必须满足以下完整契约：

1. 只允许主指针从明确拖动柄开始；
2. 至少移动 4px 后才进入拖动，单击不得触发拖动；
3. 使用 Pointer Capture 或等价机制，并校验 `pointerId`；
4. 拖动时禁用文本选择，光标和预览保持一致；
5. `Escape` 和 `pointercancel` 必须回滚，不得提交；
6. `pointerup` 只在有效目标上提交一次；
7. 长内容在上下边缘提供自动滚动；
8. 命中计算使用稳定布局坐标，不使用已被动画 transform 改写后的坐标反复计算；
9. 移动数据节点本身，不通过替换整篇文档或整份集合模拟移动；
10. 拖动结束、组件卸载和窗口失焦都必须清理监听器、光标、选择和临时样式；
11. 拖动期间关闭高成本 HoverCard、预览和动画；
12. 提供明确的放置线/目标高亮，以及可撤销或可预测的结果。

拖动必须至少测试：未超过阈值、有效移动、无效目标、跨区域、Escape、pointercancel、长内容自动滚动和卸载清理。

### 6.3 滚动

- 每个方向只能有一个主要滚动所有者。
- 固定头部和底部操作区不参与正文滚动。
- 嵌套滚动只用于有明确边界的预览、代码块、表格或独立面板。
- `overscroll-behavior` 用于阻止嵌套区域意外带动父页面。
- 程序定位内容时不得无条件抢夺键盘焦点。

### 6.4 动效

- 常规状态过渡为 100–180ms；拖动回位或面板展开不超过 220ms。
- 动效用于说明状态变化和空间关系，不用于持续吸引注意力。
- 避免大面积缩放、弹跳、发光和循环动画；持续动画仅用于真实进行中的任务。
- 尊重 `prefers-reduced-motion`，新增复杂动效时必须提供降级。

## 7. 编辑器与笔记专项标准

### 7.1 术语

- `Note` / “文档笔记”：独立 Markdown 文档，可作为标签页或分屏打开。
- `Segment Note` / “片段记录”：绑定原文片段的短笔记。
- `Annotation` / “批注”：绑定片段或文本选择的结构化记录。

界面不能把三者都缩写为没有上下文的“笔记”。

### 7.2 编辑会话

- 同一笔记同时只能有一个编辑所有者。
- 只读视图必须禁用正文、标题、格式、插入、拖动和程序化修改命令。
- 编辑权接管必须原子转移正文草稿、标题草稿、dirty 状态和保存处理器。
- `Ctrl/Cmd + S` 只作用于当前聚焦编辑器，不得广播给隐藏标签页。
- 标题和正文属于同一个保存快照，不能分别从不同版本写盘。
- 保存期间不应冻结正文输入；保存完成后必须比较版本，保留保存期间产生的新修改。
- 加载失败时编辑器默认保持只读，避免用空白内容覆盖原文件。

### 7.3 保存反馈

长文本编辑器推荐使用约 1000ms 的防抖自动保存，同时保留 `Ctrl/Cmd + S` 立即保存。若某个阶段仍使用手动保存，必须提供：

- 持续可见且准确的“未保存”状态；
- 切换、关闭和工作区变更保护；
- 保存失败后的明确重试入口；
- 不依赖进程内内存的恢复草稿，或明确说明恢复范围。

状态文案统一为：`未保存`、`保存中…`、`已保存`、`保存失败，重试`、`只读`。

### 7.4 编辑器界面

- 标题与保存状态放在同一紧凑标题栏。
- 常用文字格式保持一行；颜色、高级组件和文件操作进入菜单。
- 正文是页面主要区域，不允许工具栏因换行长期占据大面积高度。
- 正文右键默认保留系统菜单；插入组件使用 `/`、明确的“插入”入口或块级菜单。
- 块拖动遵循第 6.2 节；嵌套列表只能拖动真实列表项，不能让用户误以为移动单项却移动整组。

## 8. 文案与信息表达

- 面向用户的中文应简短、具体、可执行；代码领域术语保持工程规范定义。
- 按钮优先使用动词：保存、打开、定位、重试、移到回收站。
- 状态描述事实，不使用“似乎”“可能已经”等模糊措辞。
- 错误信息包含发生了什么以及用户下一步能做什么。
- 标题默认不重复父级上下文；需要说明所属条目时用次要文本展示。
- 日期、时长、页码和数量在同一模块采用统一格式。

## 9. 可访问性

- 交互控件必须可通过键盘到达，语义元素优先于 `div` 模拟控件。
- 图标按钮提供 `aria-label`；状态变化使用适度的 `aria-live`。
- 不只依赖颜色表达状态，至少同时使用文本、形状或图标之一。
- HoverCard 不能是访问完整信息的唯一方式。
- 表格使用正确的 header/row/cell 语义；可交互行必须有键盘等价操作。
- 文本和关键边界应满足常规对比度；`muted-foreground` 不用于关键操作或错误。

## 10. 实施流程

### 开始修改前

- 明确用户主任务和信息层级；
- 搜索并列出可复用的共享组件、hooks 和依赖；
- 确认状态所有者、保存边界和滚动所有者；
- 对拖动、删除、覆盖、切换和异步竞争做失败路径分析；
- 判断这是局部修复、共享组件修复还是设计系统缺口。

### 实现过程中

- 先修共享原语，再在业务界面组合；
- 使用语义 token，避免新增硬编码色值和孤立尺寸；
- 同一交互只保留一个状态来源；
- 不在未验证情况下复制另一个模块的复杂交互；
- 保留用户工作区中的无关修改。

### 完成后

至少执行与改动相称的验证：

```powershell
npm --workspace apps/desktop exec tsc -- --noEmit
npm --workspace apps/desktop run test:frontend
npm run desktop:build
```

并检查：

- 正常、加载、空、错误、只读、禁用和长内容状态；
- 100% 与 125% UI 缩放；
- 最窄支持宽度、默认宽度和分屏；
- 键盘、鼠标、右键、滚动和拖动；
- 标题溢出、中文换行和完整信息访问；
- 是否出现双滚动条、透明粘性表头或被遮挡的浮层；
- 控制台警告和测试中的 React/Radix/Tiptap 警告。

无法完成原生 Tauri 视觉验证时，必须在交付说明中明确标注，不得用编译或浏览器空壳代替视觉验证。

## 11. UI 改动完成定义

提交或交付前逐项确认：

- [ ] 已优先复用现有组件、库和工具；
- [ ] 没有建立重复的基础组件或状态系统；
- [ ] 主内容区与应用背景层级清楚；
- [ ] 信息密度符合桌面生产力软件，而非卡片展示页；
- [ ] 固定表头和工具栏背景不透明；
- [ ] 一个区域每个方向只有一个滚动所有者；
- [ ] 标题截断时仍能访问完整内容；
- [ ] 图标具有明确语义，纯图标按钮具备可访问名称；
- [ ] 只读和禁用状态阻止所有修改路径；
- [ ] 保存、关闭、删除和拖动失败路径已处理；
- [ ] 拖动遵循完整契约并有行为测试；
